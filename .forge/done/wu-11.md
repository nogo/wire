# Add on-demand model loading with LRU eviction

## Outcome
Wire starts llama-server processes on demand when a request arrives for a known but not-loaded model. The requesting HTTP connection is held open while the model loads. Concurrent requests for the same model coalesce — one process starts, all waiters get proxied when healthy. When running models reach `max_models`, the least recently used model with zero in-flight requests is stopped to make room. The monitor dashboard shows model state transitions.

## Values
1. Correctness — a request must never be lost or silently dropped during model loading. Either it gets proxied or it gets a clear error.
2. Simplicity — the state machine has four states, no more. No VRAM tracking, no scheduling heuristics.
3. Transparency — every state transition is logged and emitted to the monitor hub.

## Context
- `internal/process/manager.go` — after wu-10, the Manager starts warmup models at boot. `procs` map keyed by model name. `procState` holds model name, params, port, proc, healthy, startedAt, restarts. The `supervise()` goroutine handles restart loops. `buildArgs()` constructs llama-server flags. `Addr()` and `Healthy()` keyed by model name.
- `internal/config/config.go` — after wu-10, Config has `MaxModels int`, `Models map[string]ModelParams`, `Warmup []string`. `MatchModel(name)` resolves a model name to launch params via glob matching.

- `internal/gateway/affinity.go` — after wu-10, affinity table keyed by model name, initialized for warmup models only. Must be extended to register new models dynamically when they load.

## Requirements

### 1. Model state machine
Each model process has a state: `idle`, `loading`, `healthy`, `draining`. Define as a type:

```go
type modelState int
const (
    stateIdle modelState = iota
    stateLoading
    stateHealthy
    stateDraining
)
```

Add to `procState`:
- `state modelState`
- `ready chan struct{}` — closed when state transitions from loading to healthy (or to idle on failure).
- `loadErr error` — set if loading fails.
- `inflight atomic.Int64` — incremented before proxying, decremented after (via defer in handler).
- `lastUsed time.Time` — updated on each request, used for LRU ordering.

### 2. LoadOrGet method
New method on Manager:

```go
func (m *Manager) LoadOrGet(ctx context.Context, modelName string, params ModelParams) (addr string, err error)
```

Behavior:
1. Lock `m.mu`. Check if model is already in `procs`:
   - If state is `healthy`: update `lastUsed`, return addr immediately.
   - If state is `loading`: grab `ready` channel, unlock, wait on channel or ctx.Done().
   - If state is `draining`: return error "model is shutting down".
2. If model not in `procs`: check `len(running) >= maxModels`. If at capacity, call `evictLRU()`. If eviction fails (all models have in-flight requests), return error.
3. Create new `procState` with state `loading`, make `ready` channel, add to `procs`, unlock.
4. Start supervisor goroutine (reuse existing `supervise()` pattern). The goroutine starts llama-server, runs `waitHealthy()`, then transitions to `healthy` and closes `ready`.
5. The caller waits on `ready` channel or `ctx.Done()`. On success, return addr. On failure, return `loadErr`.

The load context must be detached from the caller's request context. If the requesting client disconnects, the load continues — subsequent requests benefit. Use `context.WithoutCancel()` (Go 1.21+) or a separate background context derived from the manager's root context.

### 3. LRU eviction
New method `evictLRU() error`:
1. Collect all models in state `healthy` with `inflight.Load() == 0`.
2. Sort by `lastUsed` ascending.
3. If none available, return error.
4. Transition the oldest to `draining`. Send SIGTERM. Wait up to 10s, then SIGKILL.
5. Remove from `procs` map.

Eviction is synchronous — the caller blocks until the evicted model's process exits. This is acceptable because it happens before the new model's cold start (which is much slower).

### 4. In-flight tracking
The gateway increments `inflight` before proxying and decrements after:

```go
ps.inflight.Add(1)
defer ps.inflight.Add(-1)
```

The manager exposes this via `InFlight(modelName string) int64` or the gateway accesses procState directly through a new method. The affinity table does not need changes for this.

### 5. Integrate with gateway
In `handleRoute()`, replace the 503 "model not loaded" path with:

```go
addr, err := g.mgr.LoadOrGet(r.Context(), model, params)
```

If `LoadOrGet` returns an error, write appropriate error response (503 for capacity/eviction failure, 504 for load timeout).

### 6. Dynamic affinity registration
When a new model reaches `healthy` state, register it in the affinity table. Add a method `Register(modelName string, slots int)` to `affinityTable`. When a model is evicted, remove it: `Remove(modelName string)`.

### 7. /v1/models reflects actual state
`handleModels()` lists all models in `procs` map (any state except idle) plus all warmup models. Include a status hint: loaded models show normally, loading models could include a `status` field (optional, non-breaking extension to OpenAI format).

### 8. Monitor events
Emit `ServerEvent` on state transitions:
- `loading` → log model name, trigger
- `healthy` → log model name, load duration
- `draining` → log model name, reason (eviction or shutdown)
- Load failure → log model name, error

### 9. Tests
- **Coalescing**: start 10 goroutines requesting the same unloaded model simultaneously. Verify only one llama-server process starts. All goroutines get the same addr.
- **LRU eviction**: set max_models=1, load model A (warmup), request model B. Verify A is stopped, B starts. Request A again — verify B is evicted, A reloads.
- **In-flight protection**: load model A, start a long-running proxied request, attempt to evict A. Verify eviction fails (503).
- **Context cancellation**: start loading, cancel the requesting context. Verify the load continues (detached context). Send a second request for the same model — it waits on the in-progress load.
- **Load failure**: configure a model that will fail to start (bad model ref). Verify all waiters receive the error. Verify the model transitions back to idle and is removed from procs.
- **Capacity limit**: set max_models=2, load 2 models with in-flight requests, request a third. Verify 503.

## Constraints
- `mise run check` must pass.
- Do not modify config schema — wu-10 established it.
- The load context must be detached from the HTTP request context. A client disconnect must not abort a model load that other clients may be waiting for.
- Eviction must never stop a model with in-flight requests.
- `waitHealthy` timeout should be generous (120s) — large models take time to load.
- No VRAM tracking. `max_models` is the only capacity control.

## Failure Modes
- **All models have in-flight requests at capacity**: new request gets 503. Detection: monitor shows all models busy. User increases max_models or waits.
- **Model load fails after eviction**: the evicted model is gone, the new model failed. GPU has free capacity but no model loaded. Detection: /v1/models shows no healthy models. Next request triggers a fresh load. Warmup models are not automatically restored after eviction — they behave like any other model once the system is running.
- **Slow load blocks many requests**: 50 requests arrive for an unloaded model. All hold their HTTP connections for 60s. Detection: monitor shows loading state with N waiters. Mitigation: client-side timeouts. Wire does not impose its own request timeout beyond the server's WriteTimeout.
- **Race between eviction and new request for same model**: request arrives for model A just as it is being drained. `LoadOrGet` sees state `draining` and returns error. Client retries. Acceptable — the window is small and the behavior is correct.
