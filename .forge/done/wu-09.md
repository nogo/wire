# Route requests by prompt prefix for slot affinity

## Outcome
Wire routes chat completion requests to llama-server slots based on a hash of the system prompt and message prefix. Requests sharing the same prompt prefix reuse the same slot, maximizing llama-server's KV cache hit rate. Agent workloads (repeated system prompt across many turns) see near-zero prompt eval time after the first request. When slot affinity is not possible (slot busy, no match), requests fall back to the default round-robin behavior.

## Values
1. Correctness — slot affinity is best-effort optimization. A cache miss must never cause a request failure. Fall back to default behavior silently.
2. Simplicity — minimal state in wire. The KV cache is llama-server's responsibility; wire only influences *which* slot receives the request.
3. Transparency — slot affinity decisions are observable via the monitor hub (wu-07) for debugging.

## Context
- `internal/gateway/gateway.go` — `handleRoute()` (lines 74–146) extracts the model field from the JSON body and proxies to the backend. The request body is already tee'd into a buffer (line 82). This is where the slot affinity logic hooks in: after resolving the backend, before proxying, compute a prefix hash and set the `id_slot` field in the JSON body.
- `internal/gateway/route.go` — `routeTable.resolve()` maps model name to backend name. Slot affinity operates *after* backend resolution — it selects a slot within the resolved backend.
- `internal/process/manager.go` — `procState` (lines 26–33) holds the per-backend port. The gateway already retrieves the backend address via `mgr.Addr(name)`.
- llama-server slot control: when the request JSON includes `"id_slot": N`, llama-server assigns that specific slot instead of round-robin. If the slot is busy, llama-server queues the request until that slot is free. This is the mechanism wire uses — no llama-server changes needed.
- llama-server prompt caching: within a slot, if the new prompt shares a prefix with the previous prompt in that slot, llama-server reuses the cached KV state and only evaluates the new tokens. This is automatic — wire just needs to ensure the same prefix lands on the same slot.
- `internal/config/config.go` — `Backend` struct. The number of slots per backend is not currently in config (llama-server defaults to 1, configurable via `--parallel N` in `Extra`). The affinity table needs to know slot count per backend.
- This project uses Go 1.26.

## Requirements

### 1. Prefix hashing
Function `prefixHash(body []byte) uint64`:
1. Parse the JSON body's `messages` array.
2. Extract the system message(s) content (role="system") — this is the dominant stable prefix in agent workloads.
3. If no system message exists, use the first user message content.
4. Compute a 64-bit hash (FNV-1a or similar from stdlib) of the extracted text.
5. Do not parse the full message array beyond what's needed for the prefix. Read system messages and stop.
6. On any parse error, return 0 (triggers fallback to no slot affinity).

### 2. Slot affinity table
Type `affinityTable` in `internal/gateway/affinity.go`:
```go
type affinityTable struct {
    mu       sync.Mutex
    backends map[string]*backendSlots
}

type backendSlots struct {
    slotCount  int
    assignments map[uint64]int  // prefix hash → slot ID
    lru         []uint64        // eviction order, oldest first
}
```

Method `Assign(backend string, hash uint64) (int, bool)`:
1. If hash is 0, return `(-1, false)` — no affinity.
2. Look up existing assignment for this hash. If found, move to end of LRU, return `(slotID, true)`.
3. If no existing assignment and free slots available (assignments < slotCount), assign the next free slot, return `(slotID, true)`.
4. If all slots assigned, evict the oldest LRU entry, assign its slot to the new hash, return `(slotID, true)`.

The table size is bounded by slot count per backend (typically 1–8). No unbounded growth.

### 3. Request injection
In `handleRoute()`, after resolving the backend and before proxying:
1. Compute `hash := prefixHash(capturedBody)`.
2. Call `slotID, ok := g.affinity.Assign(backendName, hash)`.
3. If `ok`, inject `"id_slot": slotID` into the JSON body. Use a lightweight approach: if the body starts with `{`, insert `"id_slot":N,` after the opening brace. This avoids a full JSON parse-and-reserialize round-trip.
4. Reconstruct `r.Body` with the modified bytes.
5. If `!ok`, proxy the original body unchanged (round-robin).

### 4. Config: slots field
Add to `Backend`:
```go
Slots int `yaml:"slots"` // Number of parallel slots (--parallel). Default: 1.
```
In `applyDefaults()`, set `Slots` to 1 when 0 (zero value). In `buildArgs()`, always pass `--parallel N` using `Backend.Slots`.

### 5. Observability
When the monitor hub (wu-07) exists, emit a `ServerEvent` (kind `EventSlotAffinity` or similar) on each affinity decision: backend, hash, assigned slot, hit/miss. This allows the monitor dashboard to show cache hit rate. If the hub is not present (monitor disabled), skip silently.

This is optional — implement only if the event channel from wu-07 is available. If wu-09 runs before wu-07, skip this requirement and leave a TODO comment.

### 6. Tests
- **Hash stability**: same messages → same hash. Different system prompts → different hash.
- **Slot assignment**: N requests with the same hash → same slot. N different hashes with M slots → round-robin across slots until full, then LRU eviction.
- **LRU eviction**: fill all slots, add a new hash, verify oldest is evicted.
- **Fallback**: hash=0 → no slot injected. Parse error → no slot injected. Request body unchanged.
- **JSON injection**: verify `id_slot` is correctly inserted and the resulting body is valid JSON.
- **Integration**: end-to-end test using `httptest.Server` — send two requests with the same system prompt, verify both have the same `id_slot` in the proxied request.

## Failure Modes
- **id_slot targets a busy slot**: llama-server queues the request until that slot is free. Under high concurrency with few slots, this could increase latency vs round-robin. Detection: monitor shows high queue depth on one slot while others are idle. Mitigation: the LRU eviction limits how many hashes compete for one slot. For backends with 1 slot (the default), affinity is irrelevant and `Assign` always returns the same slot — no behavioral change.
- **JSON injection produces invalid body**: malformed JSON causes llama-server to return 400. Detection: test with adversarial JSON bodies (nested braces in string values early in the body). Mitigation: the injection point is always after the opening `{` — insert `"id_slot":N,` as a new field. This is safe as long as the body is a valid JSON object, which is already validated by the model extraction earlier in `handleRoute()`.
- **Hash collision**: two different system prompts produce the same hash. They route to the same slot, causing unnecessary KV cache eviction. Detection: statistically negligible with 64-bit FNV. Not worth mitigating.
- **Agent switches system prompt**: the old hash's slot assignment persists in LRU until evicted. No harm — next request with the old hash goes to the old slot (miss in llama-server's cache but no error). New prompt gets a different slot.
